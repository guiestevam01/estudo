Uma técnica importante na programacao é projetar sistemas onde os desenvolvedores só precisam enfrentar uma fracao de complexidade geral. Uma das formas de abordar isso é usando a idéaia de design modular.
Design modelar é a ideia de decompor uma representacao natural em colecoes de modulos(ou classes ou subsistemas ou servicos) de modo que eles sejam independente. Isso significa que desenolvedores podem atuar em cada modulo sem necessáriamente conhecer os outros módulos.
Seu módulo mais completos defini a complexidade geral do sistema.
No geral isso é impossível em sistemas mais complexos pois em sistemas complexos esses módulos se comunicão um com os outros, chamam funcoes entre si.
Existe dependencia entre modulos: Se um módulo mudar os outros mudam para se adequar.
```
ClassA{
    static method(argsA...){
    }
}
```

```
ClassB{
    ClassA.method(args...)
}
```

Nesse exemplo, ClassB depende de ClassA, pois chama ClassA.method.

Se os parâmetros ou a assinatura de ClassA.method forem alterados, as classes que utilizam essa versão do método poderão precisar ser
modificadas para se adequar à nova interface.

A existência de dependências reduz a independência absoluta entre
   os módulos, mas isso não significa necessariamente que o design
   seja ruim, pois módulos precisam se comunicar.

Dependências fazem parte do software. O problema ocorre quando elas
   são numerosas, complexas, obscuras ou difíceis de administrar.

O objetivo do design modular é minimizar as dependências entre os
   módulos e tornar as dependências restantes simples e evidentes.

Se uma mudança que deveria estar restrita a um módulo exigir
   modificações em vários outros módulos, isso pode indicar
   amplificação de mudanças e merece uma revisão do design.

Alterar a interface pública de um método pode exigir mudanças em
   seus chamadores, e isso não significa automaticamente que o design
   seja ruim. O ideal é que mudanças na implementação interna, que
   preservem a interface, não afetem os outros módulos.
 Se um método possuir 100 chamadores e a adição de um parâmetro
   exigir a modificação dos 100 locais, é importante avaliar se todos
   realmente precisam conhecer essa informação ou se ela poderia ser
   encapsulada no próprio módulo.
Um bom módulo esconde a complexidade da implementação e oferece
   aos demais módulos uma interface menor, clara e estável.

Portanto um módulo é definido por uma interface e uma implementacao. Interface é uma 
definicao geral dos recursos que aquela classem realiza, e a implementacao seria como
ela realiza. Para chamada de módulos, devemos chamar então apenas a interface sem se 
preocupar qual seria sua implementacao. A interface defini o que o módulo faz mas não
como ele faz
Podemos entender classes e métodos(ou funcoes em não-oops) como módulos.
E cada módulo tem sua inteface(quase como se fosse assinaturas em java) e implementação.
"Os melhores módulos são aqueles cujas interfaces são muito mais simples do que suas implementaçõe"]
Interaces simples reduzem complexidade para os seus chamadores.
